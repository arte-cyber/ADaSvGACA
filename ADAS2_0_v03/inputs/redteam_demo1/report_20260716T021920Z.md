# Findings

## 1. Critical — Shellshock Remote Command Execution on Apache CGI

### Affected Target
`http://192.168.185.3:8080/victim.cgi`

### Evidence
HTTP enumeration identified Apache and CGI-related indicators:

- Server header: `Apache/2.4.10 (Debian)`
- Web path discovery showed CGI exposure:
  - `/cgi-bin/` returned HTTP `403`
- Shellshock validation against `/victim.cgi` succeeded.

The Shellshock validation command returned:

```text
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

Metasploit check also confirmed exploitability:

```text
[+] 192.168.185.3:8080 - The target is vulnerable.
```

Controlled exploitation was then performed using the approved Metasploit module:

```text
exploit/multi/http/apache_mod_cgi_bash_env_exec
Payload: linux/x86/shell/reverse_tcp
```

The controlled proof successfully opened a session and executed `id`; proof output was detected. Sessions were explicitly cleaned up using `sessions -K`, and the tool reported:

```text
session_opened: true
session_cleanup_attempted: true
session_closed: true
```

### Impact
An unauthenticated attacker can execute arbitrary commands as the web server user `www-data`. This provides a foothold on the host and may allow:

- Reading local files accessible to `www-data`
- Pivoting to other local services
- Credential discovery
- Privilege escalation attempts
- Full host compromise if additional local weaknesses are present

### Remediation
- Patch Bash immediately to a version not vulnerable to CVE-2014-6271 and related Shellshock variants.
- Remove or disable vulnerable CGI scripts.
- Restrict CGI execution where not required.
- Upgrade Apache and the underlying Debian packages.
- Add WAF or reverse proxy filtering for Shellshock payload patterns as a compensating control, but do not rely on this instead of patching.
- Review logs for suspicious `User-Agent`, `Referer`, or custom header values containing Bash function syntax such as:

```text
() { :; };
```

## 2. High — Insecure Direct Object Reference in Internal User Portal

### Affected Target
`http://192.168.185.3:5000/profile/<user_id>`

### Evidence
The application landing page exposed profile links and hints:

```html
<h1>Internal User Portal</h1>
<p>Your profile: <a href='/profile/2'>View my profile</a></p>
<p>Try: /profile/1, /profile/2, /profile/3</p>
```

The IDOR validation confirmed that changing the numeric profile ID allowed access to multiple distinct user records without changing authorization context.

Accessible profiles:

```text
/profile/1
/profile/2
/profile/3
```

Returned records included:

```json
{
  "user_id": 1,
  "data": "user=alice,role=admin,secret=FLAG{adas_hard_vm3_pwned}\n"
}
```

```json
{
  "user_id": 2,
  "data": "user=bob,role=user,notes=normal account\n"
}
```

```json
{
  "user_id": 3,
  "data": "user=charlie,role=user,notes=normal account\n"
}
```

The validation result reported:

```text
validated_vulnerability: Insecure Direct Object Reference
unauthorized_access_possible: true
authorization_context_changed: false
returned_unique_records: true
```

### Impact
An attacker can access other users’ profile data by modifying the profile ID in the URL. In this case, the flaw exposed an admin user record and a secret value.

Potential impact includes:

- Unauthorized disclosure of user data
- Exposure of secrets or flags
- Potential privilege abuse if admin-only records or actions are reachable
- Violation of access-control and privacy requirements

### Remediation
- Enforce object-level authorization checks on every request.
- Do not rely on hidden links or client-side controls to protect object access.
- Ensure authenticated users can only access objects they own or are explicitly authorized to view.
- Use non-enumerable identifiers where appropriate, but treat this as defense-in-depth only.
- Add automated access-control tests for horizontal and vertical privilege escalation cases.

`192.168.185.3:8080`

```text

```

SearchSploit lookup for the specific Apache/CGI/Shellshock context returned no direct local exploit result, but Shellshock was independently validated through CGI behavior.

Nmap NSE vulnerability scan against port `8080` did not return additional script findings.

### Impact
Running outdated Apache increases exposure to known vulnerabilities and weak default configurations. While Apache itself was not independently proven vulnerable to a separate CVE during this assessment, the outdated CGI-enabled stack directly contributed to the Shellshock attack path.

### Remediation
- Upgrade Apache to a currently supported version.
- Apply Debian security updates.
- Remove default Apache pages and sample files.
- Disable unused Apache modules, especially CGI-related modules if not required.
- Maintain a regular patch-management process.

## 5. Low — Missing HTTP Security Headers

### Affected Targets
- `192.168.185.3:5000`
- `192.168.185.3:8080`

### Evidence
Nikto reported missing headers on both web services:

```text
X-Frame-Options header is not present
X-Content-Type-Options header is not set
```

### Impact
Missing headers can increase exposure to browser-side attacks such as clickjacking and MIME-sniffing issues. These are defense-in-depth controls and were not used as a compromise path during this assessment.

### Remediation
Set the following headers where appropriate:

```http
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Content-Security-Policy: default-src 'self'
Permissions-Policy: geolocation=(), microphone=(), camera=()
```

For Flask/Werkzeug applications, consider using middleware such as Flask-Talisman or equivalent secure header configuration.

## 6. Low — Legacy SSH Algorithm Advertised

### Affected Target
`192.168.185.3:22`

### Evidence
SSH enumeration identified:

```text
OpenSSH 8.2p1 Ubuntu 4ubuntu0.13
```

Supported authentication methods:

```text
publickey
password
```

Host-key algorithms included:

```text
ssh-rsa
```

The tool flagged:

```text
legacy_algorithms_detected: ssh-rsa
```

### Impact
Advertising legacy `ssh-rsa` can allow weaker cryptographic negotiation with older clients and may violate modern hardening baselines.

No SSH authentication bypass, credential weakness, or command execution was validated during this assessment.

### Remediation
- Disable legacy `ssh-rsa` where compatibility allows.
- Prefer modern algorithms such as Ed25519 and RSA-SHA2.
- Disable password authentication if operationally feasible and require key-based authentication.
- Ensure root SSH login is disabled.
- Maintain OpenSSH security updates.
